# Quick frame — one-page structure

Read this at the end of the quick branch, when writing it out.

Save it as `FRAMED_PROBLEM.md`, in the same place a full frame would go: the project's documentation directory when one exists, the project root otherwise. Same filename on purpose — `shaping` reads it without needing to know which branch produced it, and a quick frame that gets upgraded is grown rather than replaced.

Write in English, always — including when the interview ran in another language.

```markdown
# Framed Problem: <working title>

> **Quick frame.** One person, small piece of work, days not weeks. This pass compared no
> alternative frames and ran no evidence gate. It stops being adequate if a second user
> population appears, roles or audit get involved, a competing explanation survives, or the
> work grows past a week — at which point run the full loop.

## Status
`ready-for-shape | evidence-needed | needs-reframing | stop`

## What happened
The episode, concretely: who, what they were trying to do, what got in the way, what they did
instead, what it cost. Attributed if someone said it. Marked as thin if it is thin.

## What they do today
The current way, and where it stops working.

## What would be different
The observable change that means this worked. Not a feeling — something noticeable from outside.

## Boundary
What is in, and the nearest adjacent thing that is deliberately out. Two lines.
Time budget, if there is one.

## The assumption
The one thing that, if wrong, makes this pointless. Whether it was checked, accepted as risk —
with who accepted it — or left open because nobody could answer it.

## Set aside
Anything that came up and is not being done, with *why not now*. One line each.

## Working question
The open question the solution has to answer. Solution-open: several answers should be possible.

## Context use
Where this file lives, and which project context library or documents it drew on.
```

## What is deliberately not here

No evidence ledger, no assumption ledger, no alternative frames, no options landscape table, no risk section, no confirmation block. Those parts of the full frame earn their cost on work worth weeks; on work worth days they are the reason nobody frames anything.

The banner at the top is not decoration. Six months later, this file looks exactly like a full frame unless it says otherwise, and someone will cite it as though a full pass had happened.

## Growing it into a full frame

When an upgrade condition hits, do not start a new file. Keep the same `FRAMED_PROBLEM.md`, remove the banner, and fill in the sections the full structure in `framed-problem.md` requires. What is already written — the episode, the outcome, the boundary — is exactly what the full loop would have produced for those sections, so the quick pass is never wasted work.
