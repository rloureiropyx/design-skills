The job

Eight skills that look independent, and mostly are not.

This library is a set of product design skills you install into a project. The index shows them as a flat list, which is accurate about what you can invoke and useless about what to invoke first.

A per-skill explainer can describe one step well. It cannot show the order, because the order does not live inside any single skill. It lives in the files the skills pass to each other.

Three of the eight are stages in one recipe. problem-framing, shaping, and proposal run in that order. Three more are detours you take when a stage needs them. Two are renderers that draw a decision someone else already made.

01 · The index

Eight tools, listed side by side.

The library has eight skills, and the index lists them as eight separate tools. A newcomer cannot tell which one to open first, or whether they are meant to be used together. They are used together. Most of them are steps in one recipe.

02 · The recipe

Three of them are stages.

The recipe has three stages. Work out what the problem actually is, try two or three directions and pick one, then write it up so people can decide. problem-framing, shaping, and proposal are those three stages, in that order.

03 · The interface

What crosses is a file.

What passes from one stage to the next is a file. problem-framing writes FRAMED_PROBLEM.md, shaping reads it and writes DIRECTIONS.md, proposal reads both and writes PROPOSAL.md. Nothing else crosses between them, so the decision survives after the conversation is gone.

Why a file and not a conversation. The person who approves the spend was not in the room. The person who inherits the project joins in month three. The auditor arrives after everyone has moved on. A file has a version and a reader six weeks later; a conversation has neither.
04 · Two directions

Carry it forward, or send it back.

Each stage carries the decision the last one made instead of restating it in new words. When a later stage finds evidence that contradicts the problem, it sends that back to be reframed. Rewriting the problem quietly in a later file is the failure the chain is built to catch.

The three groups. The skills sit in three folders. Process decides something, artifacts produce the thing people react to, renderers materialise a decision made elsewhere. The grouping is for people reading the repository. Copilot picks a skill by its name and description and never sees the folder.
05 · Detours

Three more hang off the spine.

Three more skills are detours, not stages. breadboarding sketches a direction in words, wireframes works out a single screen when layout is the real question, and diagrams decides what a picture should show. You reach for them when a stage needs one, and skip them when it does not.

06 · Renderers

Two come last, and decide nothing.

Two skills come last. scrollytelling builds a scrolling article and tldraw-skill draws on a local canvas. They render a decision that was already made, and they are not allowed to make one. Hand a renderer an undecided idea and it returns a polished version of the confusion.

07 · Where to start

Join wherever the earlier files exist.

You can join the chain wherever the earlier documents already exist. Start at shaping when the problem is settled, or at proposal when the direction was chosen last quarter. The one thing you cannot do is skip a document, because the next skill asks for it and stops. Start by writing the first one that is missing.

Joining work already underway

Most projects already have these documents.

They are in a thread, a slide, or someone's head. Writing the missing one down is the work that was already happening, made inspectable. Here is what each stage asks for before it will run.

problem-framing

Asks for nothing. It is the entry point. Start here when the request arrived as a solution and nobody has written down the problem it answers.

shaping

Asks for FRAMED_PROBLEM.md. It needs the slice, the time budget, and the risks. Without them it cannot tell a direction that fits from one that does not.

proposal

Asks for both earlier files. It presents a problem and a chosen direction. Given neither, it has nothing to present and nothing to ask a decision about.

breadboarding

Asks for a direction to sketch. Called from shaping, or on its own when you want places, affordances, and connections before anyone draws a box.

wireframes

Asks which screen and which rung. Zoning, lo-fi, or mid-fi. It refuses to keep going up the fidelity ladder to avoid a decision.

diagrams

Asks what the picture is for. Intention, audience, and the one thing the reader should take away, before any shape is chosen.

scrollytelling and tldraw-skill

Ask for a decision that already exists. Both stop and route you upstream when they find they are being asked to decide rather than to draw.

The payoff

Start with the first missing document.

The order is not a convention anyone has to remember. It is enforced by the files. Each skill reads what the last one wrote, so the three stages run in sequence and everything else hangs off them. Join at any point where the earlier documents already exist. Skip one and the next skill asks for it and stops, which is the chain working rather than failing.

The eight skills, one explainer each.

Three stages in order, three detours you take when a stage needs them, two renderers that draw what was already decided. Each has its own article.

problem-framing

Stage 01. Reads what already exists, recovers one real episode, tests the cause, and draws a boundary around what gets solved now. Writes FRAMED_PROBLEM.md.

shaping
