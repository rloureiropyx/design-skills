The skill · wireframes

What a wireframe settles before drawing.

It decides what a screen must do, what goes on it, and how priority reads, then hands that to a renderer to draw.

It sits downstream: shaping has already selected a direction and set the time budget, and a breadboard may have listed the affordances. The wireframe carries that direction rather than inventing one, and is reached only when layout turns out to be the real question.

Note the words a reader will see kept straight: a candidate solution is a direction, the fixed build time is a time budget.

01 · The one thing

It starts with one sentence.

A wireframe starts with one sentence, not a layout. This screen exists to let a payroll admin approve or hold a pay run. Every box added after this has to earn its place against that one job. Name the job wrong and the screen fills with things nobody needed.

02 · Page contents

List it before you place it.

Next comes a plain list of everything the screen carries, written before you decide where any of it goes. Pay period, total cost, headcount, the flagged paychecks, the approve and hold actions. Listing contents and arranging them are different jobs, and doing both at once lets the layout start driving the content. Keep the inventory dull and complete.

03 · Priority

Rank it, apart from the layout.

Then rank the contents by importance, apart from the layout. A Page Description Diagram sorts them into high, medium, and low without drawing a single box. Here the flagged paychecks and the approve control sit high, and the export link sits low. A big total at the top can own the eye while the real work sits in a table below it, so state the ranking instead of trusting size to carry it.

The axes the build skips. There are two: scale (a complete screen, a single component, a state set, or a responsive set) and depth (a concept sketch, a requirements discussion, or an implementation handoff). Both are set on purpose, and both are independent of the priority work the scene just showed.
04 · Regions

Contents become labeled regions.

Now the contents move into the boundary as labeled regions. The global nav is structural and repeats on every screen. The summary cards are a reusable module. The flagged-paycheck table and the approval bar are unique to this screen, and they get the most room because the ranking said so.

05 · Two dials

Fidelity and annotation are different dials.

Fidelity and annotation are different dials. This screen can stay grey boxes while it gathers rules, states, and behavior notes. When a stakeholder asks for more detail, they usually mean more content and rules, not real color and type. Adding polish here would tell the room the design is finished while the structure is still the open question.

06 · Sample content

Fill the boxes with content that tests them.

Sample content is a design decision, so fill the boxes with content that tests them. Symbolic values like $9,999,999.00 and MM/DD/YYYY read as their type at a glance. Then push the edges: a run with 9,999 employees, a name too long for its column, a paycheck of $0.00. If the table only survives three tidy rows, the layout has not been tested yet.

Most wireframes are templates. A page type like a pay-run review, not one specific run. Design the pattern, then prove it holds by instantiating it with one real scenario and its boundary content.
07 · Functional color

Color only when it carries meaning.

Color only goes in when it carries meaning. Grayscale by default, red for a validation error like a paycheck missing a timecard, blue for a text link and nothing else. A button reads as a button by its shape, so coloring every control blue just adds noise. Because red already means an error inside the screen, a reviewer's problem mark goes in the margin outside, where the two reds can't be confused.

08 · One scenario

One screen, one real moment.

One screen shows one real moment, not every state stacked together. The populated run, the clean run with nothing flagged, and the blocked run with missing timecards are separate variants. Roles split it further. An admin without approval rights sees the same data with the approve button gone, and each variant is drawn and linked when a decision needs it.

09 · Annotations

The behavior goes in the margin.

The behavior the picture can't show goes in the margin. Numbered notes sit outside the boundary, each on the same side as the thing it describes: who can approve, what a hold triggers, how the cards collapse on a narrow screen. The number links the note to its element, so a pointer that would cross the screen is left out. Hand this to a reviewer and they can tell you which paycheck to open first.

Where this sits against its siblings. Not problem-framing (whether to build it), not shaping (which direction), not breadboarding (the mechanism in words), not proposal (the document someone approves). A breadboard's affordances are the page-contents inventory and its connection lines are the screen's exits, so the skill carries them rather than deriving a second set. When the screen contradicts the framed problem or the selected direction, it says so and sends it back instead of restating the problem in layout.

The payoff

It tells a reviewer where to start.

A wireframe is an ordered set of decisions — one purpose, listed contents, stated priority, functional color, a single scenario, marginal annotations — made before and during the drawing rather than discovered in it. It carries a direction someone already chose, and a good one tells a reviewer where to start.
