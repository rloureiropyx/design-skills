A product design skill · How shaping works

Two good solutions. One argument that never ends.

Agreeing on the problem does not settle the solution. Two people can hold two defensible answers and have no shared test to choose between them. shaping writes the test down first, then makes the choice binary.

Scroll to run the fit check

The job

Turn a framed problem into one direction worth committing to.

Framing decides what problem is worth solving. It does not decide what to build. shaping picks up there: it writes down what a solution must do, draws more than one way to do it, and then forces a choice using a test both options were measured against.

The method is Ryan Singer’s, adapted for enterprise work. Requirements get numbers so people can argue about R4 instead of about tone. Directions get letters so a conversation can name them. Parts of a direction are mechanisms — things a user can do — not layers of a stack, because layers cannot be cut and mechanisms can.

The output is a decision with its reasoning attached. DIRECTIONS.md records the numbered requirements, the directions considered, the fit check that separated them, the time budget, and the one direction selected — so a month later the team can see not just what was chosen, but what it beat.

Diagram 01 / 10The argument
01 · The tension

Two answers, no test.

A designer wants a guided wizard. An engineer wants a batch endpoint. Both are describing a real solution to the same agreed problem, and there is no shared standard either one can be held against. This argument is not resolved by seniority; it is resolved by writing the standard down.

What is shaping, exactly? The phase between knowing what problem to solve and knowing what to build. It ends with one solution direction and the reasoning that selected it — not with wireframes.
02 · Entry

Start from the frame, don’t redo it.

Shaping reads FRAMED_PROBLEM.md and carries it forward. It does not re-derive the user, the tension, or the outcome in new words. When shaping finds evidence that genuinely contradicts the frame, it stops and sends that back — quietly rewriting the problem to fit a solution is the failure this boundary exists to prevent.

03 · Step 1

Number the requirements.

What must a solution do to count? Each answer gets a number and a status: OPEN must be met, STRETCH is welcome but optional, OUT is deliberately excluded and named so it stops resurfacing. Nine top-level requirements is the ceiling — more usually means the problem was never sliced.

04 · Step 1, continued

The requirements enterprise adds.

Roles and permissions. Auditability. The integration whose system of record always wins. Forty thousand rows instead of forty. Who supports this on day ninety. Keyboard and screen-reader behaviour. Each becomes a numbered requirement or an explicit non-requirement — because in enterprise work, silence here is what kills a project in month three.

Why numbers? Because “it doesn’t feel right” cannot be answered. “It fails R4” can.
05 · Step 3

Draw at least two.

One direction is not a choice, it is a proposal wearing a process. They have to differ in kind: fix the run at the moment it breaks, or move the work earlier so the run opens clean. A reader should be able to say in one sentence what each one gives up.

Each direction gets a breadboard. Places a person can be, what they can do or see in each one, which action takes them where — in text, too coarse to express layout. It is the cheapest way to find the missing place or the action with no destination, and it turns a paragraph into something the fit check can actually be run against. That is the breadboarding skill.
06 · Step 3, continued

Parts are mechanisms, not layers.

“UI, API, database” is not a set of parts — nothing works until all three land, so nothing can be cut. “Detect a blocker, resolve one inline, gate the close” is: each is something a person can do, and removing one leaves the rest standing. Vertical parts are what makes scope adjustable later.

07 · Step 4

If nobody can describe it, flag it.

For every part, one question: can we describe how this works? Not whether it is possible — whether we can say how. A part that fails that test gets a warning flag, and a flagged part counts as an outright failure in the check that follows. It stays one until a spike answers it. Optimism is not a resolution.

08 · Step 5

Every direction, every requirement, binary.

Each direction is scored against each requirement as pass or fail. There is no “partially”, and the absence of that option is the whole point — “partially” is how a weak direction survives a check it should have failed. The matrix does not make the decision; it makes the disagreement visible enough to have.

A failed check is a brief, not a verdict. Fix what failed and you have a new version, not a new direction: A1 → A2 → A3, left to right, each one recording what changed and why. Superseded versions stay in the document, struck through, with the reason — six weeks later “we decided not to” and “we forgot” look identical. Only the current version of each live direction appears in the matrix.
When the matrix and your judgement disagree, the requirement list is usually wrong — something that matters was never written down. Fix the list, then re-run the check. Do not overrule the matrix silently.
09 · Scope

The time is fixed. The scope moves.

Time budget is not an estimate; it is a decision about how much this problem is worth. When the selected direction does not fit, the move available is cutting scope — dropping a STRETCH requirement, removing a part — not extending the deadline. A direction that only fits by moving the date has not been worked out.

10 · Step 8

One direction, and an honest status.

Shaping ends with a selection and a status: direction-selected, spike-needed, budget-undefined, no-viable-direction, or reframe. A selected direction with a live spike attached is a real answer. A selected direction with an unknown quietly folded into it is not.

The decision after shaping

Every status has a next move.

Shaping does not automatically send every direction to a proposal. The status says what happens next, and two of the five are ways of saying “not yet”.

direction-selected

Move forward. One direction passes every OPEN requirement, fits the time budget, and carries no unresolved flag. Write the proposal.

spike-needed

Buy an answer first. A flagged part decides whether the direction is viable. Run a timeboxed spike with a written question, then re-run the fit check.

budget-undefined

Ask for the number. Without a time budget the fit check has no failure condition and every direction passes. Get the time budget before choosing.

no-viable-direction

Cut or reframe. No direction meets the OPEN requirements inside the time budget. Either the time budget is too small for this problem or the problem is too big for this time budget — say which.

reframe

Send it back to framing. Shaping found evidence that contradicts the frame. Do not rewrite the problem here; return it with what was found.

The payoff

Now it can be committed to.

A direction is not a design. It is a decision with its reasoning attached. The fit check does not tell anyone what the interface looks like, how a row behaves on a narrow screen, or what the empty state says — that is Design’s work, and it is deliberately still open. What shaping settles is the harder thing: which direction, at what cost, giving up what. DIRECTIONS.md hands the proposal a decision that can be read, questioned, and approved without re-running the argument.

The enterprise adaptation

Roles, permissions, auditability, integrations, data volume, operational complexity, and accessibility are seeded as requirement classes. They are not part of the original method and are the most common reason an otherwise sound direction fails late.
