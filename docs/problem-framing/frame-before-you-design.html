A product design skill · How problem-framing works

Frame before you design.

A request arrives already phrased as a solution. You could design it well and still answer a problem no one confirmed. problem-framing tests the problem first, and writes what it finds to one file: FRAMED_PROBLEM.md.

The job

A skill is a written procedure the assistant follows on demand.

An agent skill is a set of instructions a coding assistant loads when the work matches. problem-framing is the one it loads when a request arrives as a solution and nobody has written down the problem underneath it.

Think of it as the designer's memory for the questions that have to be answered before anyone designs. It asks them one at a time, follows the evidence, and keeps the unresolved ones visible instead of letting them pass as settled.

Its only output is a written problem. A Framed Problem records the user, the tension, the outcome, the evidence, the assumptions, the boundary, and the open question, with the evidence kept under each claim. It stays in the project, so every later sketch and decision is checked against the same intent.

01 · The stakes

A good answer to an unconfirmed problem.

A request arrives asking for an AI payroll-readiness dashboard. You could design it well and still solve a problem no one confirmed. The further the work goes, the more a wrong problem costs to correct. Problem framing tests the problem before design starts.

02 · Two ways in

Three ways in, one loop.

The skill starts a new project from a raw request, or picks up a project already underway. A third path, the quick frame, fits small solo work that still needs its problem stated. Every path runs the same loop and ends in one file, FRAMED_PROBLEM.md.

03 · Read before asking

Read the record before asking anything.

Before asking the designer anything, the skill reads the briefs, notes, metrics, and prior decisions already on record. It sorts each claim into five lanes: observation, interpretation, assumption, commitment, and preference. A quote from a real person is the ground truth, and every other line is read as an interpretation of it.

One example, running through the rest. From here on, a single SMB HCM payroll-readiness case runs through every scene below. Each question changes one visible part of the same problem, so you can watch a fuzzy initiative resolve into a boundary and a working question.
04 · Frame drift

Line up the brief against the drift.

When work is already underway, the skill lines up the original brief, the work done since, and the evidence gathered along the way. It names each gap as drift: the problem changed, scope crept, or the statement now exists to justify a solution already chosen. Eight weeks of screens are sunk cost, not evidence the frame was right.

Only when work is underway. This drift check runs only for a project that is already in progress. A new project has no brief to have drifted from, so it skips this step and goes straight to the episode.
05 · One real episode

Replace the label with one episode.

The skill replaces the feature label with one concrete episode. An SMB HR admin finalizes payroll, finds employee changes missing, chases managers, and approval slips a day. It then fixes the outcome the frame is measured by, an observable change someone outside the team could notice.

06 · Test the cause

Ask what makes it the cause.

The first explanation is usually the one that matches what the team already wanted to build. The skill offers a hypothesis, then asks what makes anyone think it is the cause. The dashboard would show the summary, but the delay comes from changes that arrive late. The weaker link gives way to the stronger one.

07 · Compare the frames

Write several frames, recommend one.

One payroll delay can support several different problems, and each points to a different design space. The skill writes three to five and compares them on evidence, leverage, ownership, and boundary. It recommends the one the observations support and keeps the rejected ones with the evidence that would revive them.

08 · Gate the evidence

Request evidence only when it moves the decision.

The skill asks for research or metrics only when the answer could change the chosen frame. An assumption has to pass four tests: it matters, the evidence is weak, more evidence is reachable, and the result would move the decision. Only then does it request one exact query, in metrics or in the research library. Otherwise it records the risk and moves on.

09 · Draw the boundary

Draw a boundary and a working question.

The team may not be able to solve the whole problem at once. The skill draws the boundary: the user, the moment, the slice handled now, and what stays out. It records the time budget as fixed build time, alongside the risks that could destabilize the work. From that boundary comes one working question, open to several answers.

10 · Hand it off

Tag the file and hand it to shaping.

The confirmed frame is written to FRAMED_PROBLEM.md and tagged with one of seven statuses. Ready-for-directions hands the file to shaping, which explores two or three solution directions and picks one. Framing buys the team time to explore solutions, not approval to build. The file stays the reference every later decision is checked against.

After the frame

Every status has a next move.

The frame is tagged with one of seven statuses, and each names the action attached to it. Framing does not send every initiative onward; the status says what happens next.

ready-for-directions

Hand it to shaping. The frame holds. Use it as the reference while exploring two or three solution directions.

revisit-directions

Reopen the affected work. The frame changed; keep the decisions still valid and revisit the ones the new evidence touches.

continue-current-frame

Keep going. New evidence still supports the user, tension, outcome, and boundary; continue while watching the known risks.

evidence-needed

Ask one targeted question. Retrieve the exact metric or research input that could change the frame, then run framing again.

needs-reframing

Return to the questions. The user, cause, outcome, or slice is not coherent enough to guide directions yet.

split

Write separate frames. The initiative holds independent users, tensions, or outcomes that should not share one direction.

stop

Do not continue. Record why the problem lacks the evidence, value, ownership, or relevance to justify more work.

A concrete output

What a Framed Problem looks like.

The questions from the scenes above consolidate into one concise project document. It states the problem, not the solution, and carries the evidence under each claim.

Project referenceFRAMED_PROBLEM.md

SMB HR admins discover missing employee changes too late

Status
ready-for-directions
Source request
"Add an AI payroll-readiness dashboard." The dashboard stays a proposed solution, not part of the problem definition.
Baseline story
An SMB HR admin tried to approve payroll, but several employee changes were missing or unconfirmed. They stopped to chase managers in chat and spreadsheets, and approval slipped a day.
Chosen problem frame
SMB HR admins discover missing employee changes only during final payroll review, forcing manual follow-up with managers and putting on-time approval at risk.
User and desired outcome
User: SMB HR admins responsible for payroll. Outcome: they identify and resolve missing changes early enough to approve payroll on time.
Evidence
In five payroll-workflow interviews, HR admins understood the payroll summary; four still delayed approval while chasing missing employee changes from managers.
Working question
How might we help SMB HR admins identify and resolve missing employee changes before payroll approval, without taking ownership away from managers?
Boundaries
  • In: readiness of employee-change inputs during the 48 hours before payroll approval.
  • Out: redesigning payroll calculation, every manager workflow, or the full HCM platform.
  • Constraint: managers remain responsible for submitting employee changes.
  • Time budget: two weeks of build time. The chosen solution must fit this fixed investment.
  • Optional boundary: supported payroll configurations are not yet defined.
  • Consequence if deferred: shaping may spread across every configuration, exceed the two-week budget, and reopen the direction later. Resolve before the proposal.
Major risk
The platform may not reliably distinguish a missing employee change from a legitimate "no change" before payroll review. If that happens, false alerts could erode HR trust and make the chosen direction unusable.
Handoff
Hand to shaping to explore two or three materially different directions. Each must preserve manager ownership, address early identification and resolution, and answer the working question; none should assume a dashboard is the answer.

The payoff

A framed problem, not a solution.

Design does not begin by choosing an answer. It begins by confirming the problem the answer is for. The loop runs end to end: read the record, sort the evidence, recover an episode, test the cause, compare the frames, gate the evidence, draw the boundary, and hand FRAMED_PROBLEM.md to shaping. Framing buys the team time to explore solutions, not approval to build. The file stays the reference every later decision is checked against.

Framed problem→Two or three directions

The whole picture

Frame, shape, propose. Then design.

problem-framing, shaping, and proposal are the three process skills that run in order, each reading the file the last one wrote. They keep the team from drifting toward the wrong problem or an unbounded solution; they do not do the detailed design themselves. Design begins once a proposal is approved.

Before Design: write the problem down, explore two or three directions and pick one, then secure the decision through the proposal. Optional boundaries may stay open only when their consequence and deadline are explicit.
The process chainThree documents, in order: FRAMED_PROBLEM.md → DIRECTIONS.md → PROPOSAL.md.
