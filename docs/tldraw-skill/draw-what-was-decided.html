A product design skill · How the tldraw renderer works

A tidy picture of an undecided idea.

“Draw me a flow” is a perfectly normal sentence with four undecided questions inside it. tldraw-skill is a renderer: it owns how to draw something well, and deliberately refuses to own what to draw.

Scroll to see where the line is

The job

Materialise a decided artifact on a canvas you own.

tldraw’s offline desktop app is a local, private, infinite canvas that saves to a real .tldraw file on disk. tldraw-skill drives it through the app’s local HTTP API — creating directions, binding arrows, laying out columns, linting, screenshotting, and saving.

It is a renderer, and the distinction is load-bearing. A flow, a journey map, a service blueprint, a breadboard, a wireframe: each has its own discipline that decides intention, audience, structure, and fidelity. This skill picks up after those decisions and does not attempt them, because nothing in the drawing mechanics knows who the diagram is for.

The output is a file, not a picture in a chat. A saved .tldraw document the user owns, opens, edits, and undoes like their own work — with the screenshot used only as the agent’s own verification.

Diagram 01 / 09The ambiguous ask
01 · The tension

Four questions inside one sentence.

“Draw me a flow for the payroll blockers thing.” Which flow — a user flow, a task flow, a cross-actor service flow? Read by an engineer or a compliance reviewer? Happy path, or errors and recovery? At what fidelity? Draw first and you get a tidy picture of an undecided idea, which is the most expensive kind, because it looks finished.

A renderer is a deliberately narrow skill. Narrowness is what lets it be good at the mechanics — and what stops it from confidently answering questions it has no basis to answer.
02 · The split

Decide over here. Draw over there.

A discipline skill owns intention, audience, artifact type, structure, and fidelity. This one owns direction records, layout math, arrows and bindings, linting, screenshots, and export. When the decisions are missing, the correct move is to ask for them or route to the skill that owns them — not to fill them in while drawing.

03 · Why this renderer

It never leaves your disk.

Not a cloud workspace, not a shared team board, not a link that needs an account. tldraw offline writes a file you own. That is the reason to pick it: unreleased roadmaps, salary bands, customer names, org charts before they are announced — the material enterprise design actually runs on.

04 · The catch

No app running, no drawing.

This is the only skill in the library that depends on something running outside Copilot: the tldraw desktop app on this machine, exposing its local API. There is no hosted fallback. If it is not running, the skill says so and stops — quietly substituting an ASCII diagram or another canvas is not a graceful degradation, it is delivering something else.

05 · The economics

One call. Return counts.

You send JavaScript, not per-element JSON, and only what you return comes back. That single property makes a thirty-direction diagram cheap: build the whole thing in loops in one file, post it once, and echo { nodes: 24, arrows: 31 }. Returning live direction records instead fills the context with noise and buys nothing.

06 · Craft

Plan the coordinates on paper first.

Column pitch, row pitch, node size — decided before the canvas gets a say, because a canvas will happily place things where they fit rather than where they mean something. And some numbers are not yours to choose: a sticky note is a fixed 200 × 200 square, so a frame sized for a wider column will always look half-empty.

07 · Craft

Bind the arrows. Always.

An arrow built from two points looks identical to a bound one and detaches the instant anyone moves a node. Since the whole value of a canvas artifact is that the reader rearranges it while thinking, a diagram of friendless arrows falls apart on first contact with its audience.

08 · The check

Three rules, then your eyes.

The linter checks exactly three things: unsized directions, overlapping text, and unbound arrows. It says nothing about arrows crossing nodes, ragged columns, or labels too small to read at the zoom anyone will actually use. A clean lint is a starting condition, not a finish line — take the screenshot and look at it, every time.

This is the anti-pattern that survives longest, because a green check is genuinely satisfying and a screenshot is genuinely work.
09 · Hand off

Saved, or it never happened.

Nothing persists until saveDoc() runs. Skip it and the canvas shows the work while the file on disk stays stale — and the user has been told it is saved. The hand-off is the file path and the document name. The screenshot was for verification; the deliverable is the file, and PNG or SVG export is a UI action the user takes.

Before you draw

What has to be decided somewhere else.

Each of these belongs to a discipline skill. When one is missing, the renderer asks rather than guesses — a guess made at drawing time becomes indistinguishable from a decision once it is on the canvas.

Intention

What is this diagram for? Aligning a team, exposing a fail point, and briefing an engineer produce three different drawings of the same system.

Audience

Who reads it, and what do they already know? Notation an engineer skims is notation a stakeholder stalls on.

Artifact type

Which diagram? A user flow, a service blueprint, a concept model and an ecosystem map answer different questions. Picking one is a decision, not a rendering preference.

Scope and structure

Where does it start and stop? Happy path only, or errors, permissions, and recovery. This decides half the directions on the canvas.

Fidelity

Zoning, lo-fi, or annotated? For wireframes especially, the rung is chosen before drawing — polish read as finality is how a sketch becomes a spec by accident.

The payoff

A drawing that survives being moved.

The point of a canvas is not the picture; it is that someone can rearrange it while they think. Bound arrows, grouped units, planned coordinates and a saved file are what make that possible — and each one is invisible in a screenshot, which is exactly why they get skipped. Keeping the decisions upstream and the mechanics here is what lets both be done properly: the discipline skill argues about what the diagram should say, and the renderer makes sure it still says it after the reader drags a box.

Where this one comes from.

This skill is vendored from a personal library and adapted to ship. The adaptation is most of the interesting part.

tldraw offline

The desktop app, its local HTTP API, and the .tldraw file format. Version 1.12.0 is what the mechanics here are written against — including its quirks, like a screenshot bounds option that silently returns a window capture.

What vendoring changed
