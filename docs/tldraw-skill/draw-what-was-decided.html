The job

A renderer draws a decision it did not make.

This library is a set of product design skills. Most of them decide something: what the problem is, which direction to build, what a picture should show. Two of them decide nothing and draw what the others settled. tldraw-skill is one of those two.

It draws on a local tldraw canvas: a flow, a journey map, a service blueprint, a sitemap, a breadboard, a set of wireframes. Deciding what to draw and drawing it well are different jobs, and the split between them is the whole design of this skill.

Bring it a decision. A discipline skill works out intention, audience, artifact type, structure, and fidelity. This one places the shapes, binds the arrows, checks the result, and saves the file. Two facts decide whether it works at all: the work stays on the machine, and it needs the desktop app running.

01 · The ask

One ask, four holes.

Someone asks for a flow for the payroll blockers. Which flow, a single user's path or a service flow across several actors? Read by an engineer or by a compliance reviewer, showing the happy path or the errors too? Draw before those are answered and you get a tidy picture of an idea nobody has decided.

02 · The split

Two skills share the work.

Two skills share the work. A discipline skill decides intention, audience, artifact type, structure, and fidelity. This one places the coordinates, binds the arrows, runs the lint, and exports the file. When those decisions are missing it asks for them instead of inventing a plausible answer.

03 · The dependency

It has to be running.

Here tldraw is the offline desktop app, and the skill talks to its local API on the same machine. There is no hosted fallback. If the app is not running, the skill says so and stops rather than drawing somewhere else.

Installing and starting the app. The tldraw offline desktop app has to be downloaded and launched before the skill can reach it. The skill reads the app's port and token itself, so once it is running there is nothing to configure. When it cannot reach the app it stops and says so rather than drawing on another canvas. The same choice rules out collaboration: no sharing, no comments, no co-editing. A request for a collaborative canvas has no renderer in this plugin.
04 · Local vs cloud

Yours, on disk.

The reason to pick tldraw is that the work stays on the machine. It writes a real .tldraw file you own instead of a cloud workspace or a shared board behind a login. That fits unreleased roadmaps, salary bands, and org charts before anyone announces them.

05 · One exec

One call in, counts out.

You send JavaScript, not per-element JSON, and only what you return comes back. One call can build a thirty-shape diagram from a loop and echo back the counts. So the working style is to build in loops and return numbers, never to drip-feed shapes across separate calls.

06 · The grid

Plan the grid first.

The grid gets planned on paper before any shape exists. Column pitch, row pitch, and node size are set to real numbers, because a canvas places things where they fit rather than where they mean something. Some numbers are not yours to choose. A sticky note is 200 units wide and that width is fixed.

07 · Bound vs loose

Bind the arrows.

An arrow built from two loose points looks identical to a bound one on screen. The difference shows the moment someone drags a node, when the loose arrow detaches and the bound one follows. A canvas artifact exists to be rearranged while people think, so every arrow is bound to the shapes at its ends.

The shapes worth knowing. Five cover almost everything: frames hold a screen, geo nodes are the boxes, sticky notes carry a thought, bound arrows connect two shapes, and text labels the rest. Some of their properties are the skill's to set and some are not. A sticky note is 200 units wide and grows in height as the text runs on; that width is fixed, not a number you pass.
08 · The annotation layer

Annotate from the near gutter.

Notes about the drawing sit in the margin, each on the same side as the thing it describes. A number goes on the target and the same number opens its note, so the two read as a pair without a line between them. When a connector would cross the drawing to reach its note, it gets dropped. An arrow reaching over a wireframe ends up louder than the wireframe.

What it will not draw. This renderer draws an artifact someone has already decided on. It does not decide what a breadboard contains, and it does not choose what a diagram should show. When the thing you need is an argument that unfolds as you read, that is a scrollytelling article, and when it is a document someone signs off on, that is a proposal written in prose. Bring this skill a decision and it draws it.
09 · Finishing

Done means saved.

A clean lint is a starting condition, not the finish. It says nothing about arrows crossing nodes or labels too small to read, so the loop ends with a screenshot and a look. Nothing reaches disk until saveDoc() runs, and skipping it leaves the canvas updated while the file stays stale. The hand-off is the path to the .tldraw file and the name of the document.

The payoff

The deliverable is the saved file.

A discipline skill decides what to draw; this one places it, binds it, checks it, and saves it. That split is the whole skill. Two facts decide whether it runs at all: the work stays on your machine in a .tldraw file you own, and the offline desktop app has to be running for the skill to reach it. Hand it a decision and it draws it. Hand it an undecided idea and it stops and asks.
